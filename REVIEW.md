# REVIEW.md

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | create_employee / list_employees / punch_in | The starter hard-coded default Mongo connection values and did not respect env precedence cleanly; it also never created required indexes. | Health checks and repeated test runs showed no startup index guarantee and no explicit env-driven configuration. | The application now reads MONGO_URI and MONGO_DB from process env with a local fallback only and creates startup indexes idempotently. |
| 2 | compute_late_minutes / compute_overtime / compute_work_hours | The helper logic ignored the IST-date and overnight-shift requirements from R1-R5 and used naive date math. | Reproducing overnight shift and late-minute edge cases gave the wrong result or a misaligned attendance date. | The implementation calculates based on IST-aware datetime handling and applies the attendance-date logic defined by the spec. |
| 3 | punch_in | The starter used a check-then-insert pattern and could silently allow duplicate same-day records under concurrency. | Two simultaneous punch-ins could both observe no record and both insert. | The code now uses a unique composite index on (emp_code, date) and duplicate-key handling to guarantee exactly one success. |
| 4 | list_employees | Pagination was incorrect because it skipped page * page_size rather than (page-1) * page_size, and it counted total records without filter-aware semantics. | Page 2 returned incorrect rows and total was not based on the filtered set. | Pagination uses offset = (page - 1) * page_size and total is computed on the filtered query. |
| 5 | punch_in | It returned an id field that is not part of the API contract and did not preserve the exact API response shape. | Responses did not match the schema in openapi.yaml. | Serialized output now matches the documented schema with emp_code/date/status/punch_in/punch_out/work_hours/... fields only. |
| 6 | punch_out | No implementation existed for the punch-out contract, including validation for punch_out > punch_in, 24-hour limit, and concurrency. | The endpoint was missing entirely; there was no matching status or result semantics. | The endpoint was implemented with atomic update filtering and checked validation against the contract. |
| 7 | attendance list | The starter loaded and sorted the whole collection in Python, which is not appropriate for large datasets and does not honor filter semantics or page-size limits correctly. | Large collections would be slow and the query logic was not efficient. | The endpoint uses Mongo query filters and a DB sort with skip/limit. |
| 8 | /attendance/{emp_code}/{date} | The regularization endpoint did not exist and there was no audit history / recomputation logic. | Manual correction requests would fail with missing route or wrong semantics. | The patch endpoint now validates, recomputes derived fields, and appends a single audit entry per successful correction. |
| 9 | analytics endpoints | The starter had no Mongo aggregation for monthly summaries, department summaries, leaderboard, or department trend. | The app had no analytics and could not satisfy the assignment. | These endpoints were implemented as Mongo aggregation pipelines with the required filters, ranking, and rate calculations. |
| 10 | /admin/explain/{endpoint} | The requirement was absent from the starter. | The grader expects explain output with the main query/aggregation in raw JSON. | The endpoint was added with endpoint-specific explain plans. |

## Not a defect

- The starter's overall app object and health endpoint were acceptable as a foundation; they aligned with the expected FastAPI structure and basic readiness check, so they were retained and hardened rather than discarded.
- The database and collection names were acceptable as a default; the fix was to honor env variables without hard-coding credentials.
